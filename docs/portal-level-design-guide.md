# Portal 关卡设计经验与验收指南

> 适用范围：Cleared 普通主线中的 Portal 关卡内容设计。
>
> 规则实现、状态机和数据字段仍以 [`portal-mechanic.md`](portal-mechanic.md) 为准；
> 本文只约束“什么样的题面值得发布”。

## 1. 先守住普通玩法

Portal 不是独立小游戏。玩家最终仍要连接所有同色端点，并用互不重叠的路径
覆盖所有必填格。传送门只改变其中一条或少数线路的拓扑，不应取代多色线路之间
原本的空间分配。

判断一个 Portal 题面是否成立时，先暂时隐藏门图标，把门格视为不可经过的空洞：

- 端点分布本身是否像一关完整的 Cleared；
- 是否至少有数条线路会争夺通道，而不是只有一条长蛇负责填满棋盘；
- 玩家是否需要决定先后顺序、边界归属或转弯空间；
- 增加 Portal 后，是否出现新的空间判断，而不只是缩短一段路。

普通层不成立时，增加门的数量、拉远门的距离或增加路径转弯都不能补救题面。

章节也不必每关都出现 Portal。63–97 采用普通题与双门题混排，普通关继续承担
高阶空间规划；Portal 是变化题，不是必须填满每个关卡槽位的标签。

## 2. 当前内容边界

在 100 关以前，Portal 关遵守以下产品边界：

| 项目 | 当前要求 |
| --- | --- |
| 棋盘 | 8×8 高阶混合章；前置里程碑关可使用更小棋盘 |
| 门格 | 每关恰好 2 个，属于同一个 `P1` 网络 |
| 规则 | `portal@2`，每条线路最多传送一次 |
| 棋子种类 | 8×8 硬下限 4 种；Portal 常态 5–8 种，后期普通题可到 9 种 |
| 组合机制 | 不加入炸弹、重走、单向门或移动门 |
| 初始说明 | 所有 Portal 关统一显示“路径会通过传送门抵达另一个传送门” |
| 到门说明 | `PORTAL_LOCKED` / `PORTAL_WAIT` 统一显示“到达传送门后松手，再从另一扇门继续”；出口续接后隐藏 |

四门网络属于后续能力。只有在 100 关以后安排过明确的四门选择教学，才可以把
`Portals[0].Cells` 从 2 个增加到 4 个。门数不是当前难度旋钮。

现有第 32、47 关的三门题面属于早期内容，仍需在对应重做批次收敛到本节边界。
63–92 已全部按混排方案重做，93–97 延续追加，其中 Portal 题均为两个门格。

## 3. Portal 可以是必需路线，也可以是高成本捷径

每关在发布审查中必须归入以下一类：

1. **Portal 必需**：禁止经过门格后不存在完整覆盖解。
2. **Portal 可选但不简单**：存在无门解，但需要重新分配多条颜色的区域；不能只把
   Portal 线路沿相邻格直接接回去。
3. **廉价旁路**：无门解更短、更直或一眼可见，其他颜色几乎不需要改变。此类拒绝发布。

“标准解必须使用 Portal”只是解答数据约束，用来验证传送流程；它不等于题面必须
逻辑唯一。允许玩家发现高质量的无门解，但必须把它当成一条经过审查的第二解，记录
其完整路径并实际回放。

只保存一条“看起来改了很多颜色”的无门解不够。当前高成本旁路门槛是：固定官方解
中的其余线路时，仅放开 Portal 线路，或放开 Portal 线路加任意另一色，都必须无解。
这样才能证明至少三色需要偏离官方布局；这仍不是对人类难度的绝对保证。

## 4. 量化门槛

自动检查负责拦住明显不合格的题面，不能代替试玩。

### 4.1 硬门槛

- 8×8 至少 4 色；63–67 使用 5–6 色，68–92 使用 6–9 色。
- 当前每关恰好 2 个门格，且都不是端点或阻挡格。
- 标准解恰好包含一次 Portal 跳转，并覆盖全部 64 格。
- 标准线路原则上至少 5 格；若因封口需要保留 3 格以内线路，整关最多 1 条并须人工说明。
- 最长线路目标不超过标准解覆盖格的 30%，硬上限 35%。
- 不设置逐关 `Instructions`；统一两句文案由 `src/ui/portal-instructions.js` 按阶段提供。
- 题面、分段解答、Portal 校验和 `GameRunner` 回放必须同时通过。

63–67 首批重做采用更严格的内部线：每条线路 8–16 格，最长线路占比不超过
25%，没有 3 格以内线路。
68–92 的实际标准线路为 4–15 格，也没有 2–3 格凑数线。

### 4.2 人工审查

- 门两侧是否分别处在有意义的区域，而不是固定塞在角落；
- Portal 线路是否会改变至少另一条线路的空间选择；
- 最短、最直的端点是否过多，导致颜色数量只是表面数字；
- Portal 线路不能每关都固定为第一种颜色；
- 无门解若存在，是否排除了只改一色或两色的廉价方案；
- 逆向连接、不同作答顺序和误触回滚是否仍然自然；
- 小屏上能否分辨端点、门格和狭窄通道。

## 5. 推荐设计流程

### 5.1 从均衡多线骨架开始

先设计或选取一份合格的普通 8×8 完整解。路径应长度接近、分布交错，并有真实的
区域竞争。可以重新组合已验证的路径骨架，再旋转或镜像；不能只把旧题整体旋转、
镜像或换色后当成新关卡。发布检查应对八种对称变换做题面去重。

不要先生成一条覆盖全盘的 Hamilton 路径，再把它切成很多颜色。那种流程很容易得到
“一条 45–57 格主线 + 多条相邻短线”，只能证明可解，不能产生可靠难度。

### 5.2 用 Portal 重组两个区域

从两条已有路径各选一个内部格作为门格：

1. 保留第一条路径从端点到入口门的部分；
2. 通过 Portal 接到第二条路径的出口门；
3. 从出口继续到第二条路径端点；
4. 把两条原路径的剩余部分重新组成完整普通线路；
5. 再调整端点和线路顺序，使 Portal 颜色不会被数据顺序泄露。

这种做法让传送线路与其他颜色共享原有空间预算，比较容易保持线路均衡。

### 5.3 同时审查有门解和无门解

- 标准有门解用于发布数据、提示和规则回放；
- 离线搜索把两个门格视为不可走格，判断是否有无门完整解；
- 若有无门解，保存一份审查用路径，比较每条线路长度、转弯和区域重分配；
- 固定其他官方路径，逐个排除一色和两色就能完成的无门旁路；
- 不以“解的数量”单独判断难度，优先检查是否存在明显廉价旁路。

使用 `node scripts/solve-no-portal.js` 可审计本章所有 Portal 题，追加显示编号可审计
单关。工具最多支持 8×8，状态上限为 250000；`limit` 只能解释为未知，不能当成无解。

### 5.4 名称只作设计记录，界面统一数字

名称可描述空间主题，例如“中轴换位”或“边界折返”，但只保留在内容数据与设计记录中。
主线游玩标题统一为“当前关卡 / 总关卡”，不显示名称或逐关说明。Portal 只使用两句
共享状态提示；独立试玩已经删除，前置里程碑教学关仍保留。

## 6. 难度递进建议

| 区间 | 棋子 | 普通 / Portal | 主要变化 |
| --- | ---: | --- | --- |
| 63–67 | 5–6 | 0 / 5 | 首批均衡双门题 |
| 68–72 | 6–7 | 4 / 1 | 普通玩法重新成为主体 |
| 73–82 | 6–8 | 6 / 4 | 瓶颈、顺序、中心与边界互锁 |
| 83–92 | 7–9 | 6 / 4 | 更紧的空间预算与综合考核 |
| 93–100 | 依试玩调整 | 继续混排 | 不增加门数 |
| 101+ | 视章节而定 | 继续混排 | 先教学四门选择，再引入多出口误导 |

递进应来自端点关系和空间约束，不来自机械地增加门数或添加短线。

## 7. 数据与解答检查

题面继续使用稳定 ID 和 Portal v2 数据：

```js
{
  Id: 'portal-8x8-01',
  Mechanic: 'portal',
  PortalRulesVersion: 2,
  Width: 8,
  Height: 8,
  Lines: [/* 5–7 对端点 */],
  Portals: [{ Id: 'P1', Cells: [entry, exit] }]
}
```

标准解使用分段格式，且只在真实门格间声明跳转：

```js
{
  Segments: [
    {
      Cells: [/* 起点到入口 */],
      Exit: { PortalId: 'P1', From: entry, To: exit }
    },
    { Cells: [/* 出口到终点 */] }
  ]
}
```

修改 `clearedset*.json` 后必须运行 `node scripts/generate-level-modules.js`，再运行
`node tests/run.js`。生成的相邻 JS 文件不得手改。

混排中的普通关不声明 Portal 字段，完整路径放入
`ordinary-chapter-solutions.js` 的 `ByLevelId`。历史 `portal-8x8-*` ID 保留为稳定身份，
不能根据 ID 前缀启用机制；规则只由 `Mechanic` 与版本字段决定。

## 9. 常见反模式

- 用一条超长线路承担 70% 以上棋盘，再用短线补洞；
- 用大量 2–3 格线路伪造“颜色更多、难度更高”；
- 把额外门格当难度档位，却忘记 v2 未使用门不计必填覆盖；
- 所有关卡都把 Portal 线路放在同一个颜色序号；
- 只验证官方解能通关，不搜索无门旁路；
- 只挑一条复杂的无门解展示，却不排除另一条廉价无门解；
- 给每关重复编写操作说明，导致与共享两句状态提示不一致；
- 仅依靠传送距离、转弯数或关卡名称推断难度。

## 11. 68–92 混排重做记录

本批为 16 个普通关与 9 个双门关。Portal 位于 70、73、76、79、82、84、87、89、92；
76、84、89 保留高成本无门解，其余六关无门完整覆盖无解。全部题面和质量指标见
[`8x8-portal-level-pack-design.md`](8x8-portal-level-pack-design.md)。

`mixed-chapter.test.js` 同时固定混排位置、颜色数、无凑数短线、对称去重、官方解、
完整提示、无门分类及一/二色旁路反证，避免“工程可运行”再次被误当成“设计已合格”。

## 12. 93–97 追加记录

本批 3 普通＋2 双门，Portal 位于 94、97，均为必需路线。五关使用 7–9 色，
每条标准线路 5–14 格，最长占全盘 21.9%；标准解覆盖 64 格，未加入四门或组合机制。
除常规内容校验，增加反向连接、换顺序回放、完整提示逐格比对，以及旧 92 关存档
连续解锁新五关的回归。静态图核对不能代替人类难度与真机验收。

新增主线同时涉及独立后端的合法关卡目录。客户端追加并不自动扩展云端目录；
目录对齐与部署是联网发布前置条件，不得绕过已有云端权威。逐关指标、设计重点及
本次未部署边界见 [`8x8-portal-level-pack-design.md`](8x8-portal-level-pack-design.md) 第 9 节。
