# 本地结算＋偶尔云备份

首发决定（2026-09-08）：用户明确暂不启用“本地直接发币＋云端偶尔备份”。本次送审／首发继续使用本地保存＋低频批量云结算，金币到账与货币购买仍由云端确认；保留已开放的正常新玩家全量准入及 138 关目录，不改变请求节奏或存档规则。

入口收敛（2026-09-08）：`game.js → bootstrap.start()` 已只装配低频云结算方案；`cloudConfigForEnvironment` 对 develop／trial／release／unknown 均固定返回 `localBackupEnabled:false`，开发本地覆盖也不能重新开启。正常启动不再读取备份空档状态、创建 `BackupSnapshot`／`CloudBackupService` 或把 backup 注入 App／ProgressSyncService。历史组件、四种存档编码、旧档数据和恢复记录继续保留；已有 `local-backup` 档在无备份能力时仍以 `not-configured` 失败关闭，不会自动转成云权威。

新模式的 P1、P2 及 P3 本地代码、自动化测试和文档保留，客户端 `localBackupEnabled:false`、后端 `BACKUP_WRITE_ENABLED=false` 保持不变；暂不部署／启用新备份协议或生成相应预览，不清理现有存档、待办或代码。其部署和专项真机验收不属于本次首发前置，未来是否启用须另行明确授权，并按届时版本复核存档兼容和验证范围。当前候选包的新账号、通关／重进、第 138 关及微信发布检查仍需完成。以下审查记录和[实施方案](local-settlement-cloud-backup-plan.md)保留为新模式的历史设计与验证证据，不代表启用授权。

审查修复（2026-09-07）：冲突版本会持久阻断普通上传，只有当次明确确认可使用待确认版本；云读取在恢复完成前不接受远端版本或指纹。备份逐域重新读取可靠落盘数据，读取失败或损坏会停止上传。旧购买待办先走原恢复路径，未确定前不切换模式。恢复会保留每日历史但隔离未选中完成的奖励证据，结果页也按本地保存失败与旧云同步等待分别提示。

复审补充（2026-09-07）：普通结果页连续重试金币保存失败时，仍保持“本地保存未成功，点击重试”，不回退为“奖励待同步”；存储恢复后重试正常到账并落盘，再次重试不重复发奖。回归测试先复现旧实现失败，再验证修复；本次仅修改结果页重试分支、对应测试和本记录，不涉及后端或启用配置。

结果展示调整（2026-09-07）：当前预览配置仍沿用旧云结算。普通／每日结果页在等待回执时直接显示现有配置的“首通奖励 100／500 货币”，不显示“奖励待同步”或提供点击同步热区；已确认到账显示“获得 X 货币”，已领取不暗示再次发奖，明确拒绝显示“奖励未到账”。这是奖励额度展示，不会写余额或提前标记到账。本地保存失败仍显示保存重试提示；云同步／备份操作仍在主页和账号页处理。本次不启用本地结算或部署云函数。

即时余额显示（2026-09-08）：首页和货币购买确认现在显示“云确认余额＋当前账号可靠待办中的未确认首通奖励”。普通按有效 `levelKey`、每日按完整两关的 `dateKey` 去重，金额只取客户端既有 100／500 配置；`RewardUnlockService.view()` 的确认余额、领取标记和永久拥有权不变。这个显示合计不写盘、不上传，也不是消费凭证；购买仍先同步待确认收益，再由云端确认扣款。断网、在途和可重试结果保留显示，云确认后不双加，明确拒绝后回落；本地保存／入队失败不增加显示。账号、环境、绑定或存档归属无法确认时显示不可用且不暴露旧账号确认余额；归属可信但处于只读／迁移／回执应用／恢复保护状态时只显示确认余额，不推算待确认增量。

## 每日新内容的联网合同

2026-09-16 至 10-23 的连续 38 天排期（[十天机制包](daily-mechanic-pack.md)及[未来四周关卡包](daily-four-week-pack.md)）沿用 `daily-YYYY-MM-DD-v1`，两项 levelId 分别追加 `-intro-v1`、`-extreme-v1`；每日默认三次进入、两关完成一次 500 奖励不变。Portal/冰封题面与解答不进入同步 payload；服务端接收原 `DAILY_ENTRY_RECORDED`/`DAILY_LEVEL_COMPLETED`，按固定 dateKey 和两项 ID 校验、幂等结算。跨北京时间午夜完成仍归进入时日期。

因此新增这些客户端日期不需要修改普通关卡目录或改变既有云协议。日期题面与混合运行时必须随新微信客户端上传才会到达玩家；本轮没有重新部署服务器，现有兼容结论不等于客户端已上线，也不启用 local-backup。

## 当前实际启用：低频云结算

这与下节已实现但未启用的 `local-backup` 不同。当前 checked-in 预览／release 配置均为 `localBackupEnabled:false`；手机旧预览是否已包含这些客户端配置，须以重新编译的候选包为准。

- 启动确认身份并读取云档，新玩家首次建档。普通游玩先本地保存并登记待办；金币到账与货币购买仍由云端确认，云端不是单纯保存一份快照。
- 已可靠入队但尚未云确认的普通／每日首通奖励会加入首页与购买弹窗的显示合计；确认余额和领取状态仍保持云权威，重启从原待办重建，不新增钱包或存储字段。
- 同一运行会话内，自动检查点通常至少间隔 60 秒；失败逐步退避、最长 5 分钟。游玩变更累计 5 次关卡完成、40 条待办，或待办达到 3 分钟后的下一次持久变更，可触发批量同步。
- 回主页、进入账号页、切后台／回前台都可能触发同步并受上述间隔限制。无待办时，切后台不刷新；其他节点距上次成功不足 5 分钟则跳过。没有定时轮询，也不是每 3／5 分钟自动发请求。
- 手动重试可绕过冷却；货币购买可能先同步待确认收益，再请求购买。一个同步流程可能有身份／状态读取和多批 `sync.push`，每批最多 50 条、单次最多 4 批，不等于一次备份请求。
- 当前账号页把同步状态收进同一行：无待办且最近状态成功时显示“已同步至云端”，本地有待办时显示“立即同步”，失败时才显示“重试同步”。页面不显示“恢复云备份”；该入口只在 `local-backup` 真正启用时出现，避免把未开放能力呈现成不可点击选项，底层恢复实现仍保留。

实际入口为 `ProgressSyncService.atCheckpoint`、`App.resumeOnline/onHide/requestRewardUnlock`；本次仅说明当前行为，没有切换模式或改动请求节奏。

启动分派的职责、兼容状态和验证矩阵见[云结算模式收敛方案](cloud-settlement-mode-consolidation-plan.md)。该收敛只整理现有入口并保持云结算、备份、迁移和恢复协议；它不构成启用 `local-backup`、迁移玩家存档或改变请求节奏的授权。实施中确认：若持久化存档已是 `local-backup`，但当前客户端未开启或未注入备份能力，启动会复用 `not-configured` 失败关闭，不发云结算／备份请求，也不改变本地权威和数据；现行候选配置和正常云结算路径不变。

单方案入口的施工边界、测试映射和本地实施记录见[单方案结算：实施方案与严格代码施工边界](single-mode-settlement-plan.md)。当前只取消正常启动的备份装配和配置启用入口；历史备份代码、旧存档编码和迁移／恢复保护仍保留，不代表兼容代码已物理退役或旧档已转换。本轮单方案结算真机测试已于 2026-09-08 登记为通过（用户确认），范围和证据边界见该文档第 8.1 节；代理未独立核验设备与云日志。

## 独立 App `app-local` 不是微信 `local-backup`

P2.5-C 已为未来独立 App 实现另一份共享本地权威合同。它只在仓库外宿主 H 显式提供 `mode:'app-local'`、独立非空存储命名空间，以及 `progress/economy/entitlements/stamina/preferences = app-local`、`daily = disabled` 的完整六域映射时成立。宿主平台还须同步报告匹配的 `{ id, isolated:true }`；组合根会在创建 App、有状态服务或读取业务存储前完成检查，并拒绝不完整、额外或混合权威。

`app-local` 不创建或注入 SyncStore、ProgressSync、Economy、身份、云备份、在线／每日服务，不生成云待办，也不上传六域快照。它不是本节下方历史 `local-backup` 的新名字、降级路径或启用开关；微信网络失败、CloudBase 缺失、备份能力缺失和旧 `local-backup` 档都不得自动切换到它。App 中若存在 SyncStore，原同步权威始终优先；任何混合或不完整配置失败关闭。

当前实现只证明共享业务的逻辑隔离和路由：同步失败存储、重启补办及不同测试命名空间中相同逻辑 key 互不可见均有 Node 回归，但不能证明原生容器已提供物理隔离、可靠提交、杀进程恢复或设备迁移。这些证据仍须在 P4／P4.5／P5 的实际宿主、模拟器或真机边界取得。现有微信云权威、历史 `local-backup` 代码、配置、存档 key、协议及此前设备／云端记录均不因本节改变。

## 已实现但未启用：本地结算＋备份

- 新 `local-backup` 模式下，普通／每日通关、金币、游戏币购买、体力和设置由各自现有服务在本地保存。保存成功后立即展示结果；保存失败保留重试入口，不等待或伪造云确认。
- 业务变更只增加当前账号范围的本地版本并标记待备份，不生成旧 `sync.push`／`economy.purchase` 操作，也没有后台计时器。
- 回到主页或进入账号页时，仅在有变化且距最近一次尝试满 3 分钟时调用一次 `backup.commit`。手动“立即备份”绕过冷却；重复触发共用同一在途任务。无变化为零请求，切后台／回前台不单独上传。
- 每次上传固定一份已保存的六域快照。上传期间出现的新变化不会被旧 ACK 清除，也不会用 ACK 中的旧资产覆盖本机。
- 快照只含普通进度和最后位置、当前日挑战投影及领奖去重、当前余额与永久资产、体力和当前设置。单快照预算 256 KiB，新协议请求／响应预算 288 KiB；超限失败且保留本地完整数据。

## 恢复与冲突

- 启动前先检查现有业务存储 key。确实空白的本地档在身份确认后读取一次 `backup.read`，有云档才自动恢复；读取失败不是“云端无档”，不会自动覆盖未知云档。
- 非空本地档绝不自动下载覆盖。账号页“恢复云备份”先读取并显示替换确认；读取等待期间若本地版本变化，确认失效并要求重新读取。
- 恢复先把一条任务写入 `SyncStore`，再逐域落盘。中途中断时禁止继续游玩，重启后重放同一任务；完成后才清除任务。恢复不会重放通关、广告或分享事件，也不会额外补发奖励。
- `backup.commit` 使用云版本比较。旧基础版本返回冲突，不自动合并或取最大余额；玩家可以继续保留本机，或明确选择覆盖云备份／恢复云备份。再次冲突则停止。
- 账号、绑定 epoch、环境或本地模式已变化时，所有异步读写回调都拒绝应用。

## 兼容和启用边界

旧 `cloud-authoritative`、迁移、operation 队列和回执恢复代码保留，用于先处理当前开发测试档中真实存在的旧待办。只有旧待办、购买和应用日志均已确定结果后，才为该测试账号启用 `local-backup`；不会清队列、清缓存、补币或把绑定账号伪装成游客。

以下是备份协议仍作为候选时留下的历史启用门槛；正常入口收敛后，仅修改内部预览配置已不能重新启用它，未来若重新选择该方案必须另行授权启动装配和完整复验。源码默认 `localBackupEnabled:false`，后端 `BACKUP_WRITE_ENABLED=false`。原门槛要求先创建并回读私有 `player_backups` 集合和拒绝客户端直读写规则，部署并验证含 `backup.read/backup.commit` 的 `player-state-api`，只对白名单测试账号打开专用 `backup` profile，最后才考虑内部预览配置。此次送审 release 仅开启云结算，备份开关保持关闭；不得直接对已全量准入的后端开启未经验证的历史模式。

## 验证边界

本地自动化覆盖：断网首通／重复通关／购买／保存失败、游戏过程零云结算请求、3 分钟冷却、无变化零请求、在途复用、旧 ACK、空档恢复、读取失败、读取竞态、中断恢复、冲突确认及取消／重启、未完成购买阻断切换、恢复后奖励证据隔离、服务端重复请求和双设备并发。

当前单方案的真机测试按上述用户确认登记为通过；未提供设备型号、测试包版本、逐项记录及原始日志，不将该结论扩展为历史备份方案的两台真机冲突、备份写入／恢复或启用验收。微信开发者工具编译与预览、独立后端日志核验和正式发布验收仍需分别确认；Node 模拟和函数包校验本身不等于手机或线上已经生效。
