## 1. 结论与建议

当前最值得处理的是主包 BGM，不是继续拆主题，也不是删玩法代码。

- 开工主包源码估算 **3,181,355 bytes / 3.034 MiB**，总包 **16,472,295 bytes / 15.709 MiB**。
- BGM 为 **1,682,092 bytes / 1.604 MiB**，占主包 **52.87%**。这里的 1.682 是十进制 MB，不是 MiB。
- 十套正式主题已在普通分包内，总图像 13,289,490 bytes / 12.674 MiB。再次声称“拆出十套主题可给主包减少 12.67 MiB”会重复计算已有收益。
- 当前 BGM 已是 205.08 秒、双声道、32 kHz、约 64.3 kbps AAC，不能假设是未压缩高码率音频，更不能承诺无损缩小一半。
- 已按接受首次 BGM 延迟的路线实施：**基线与排除项 → Portal 无损候选 → BGM 普通分包**。当前主包源码估算 **1,425,033 bytes / 1.359 MiB**，开发者工具本地分析显示 **1.36MB**，达到 **≤1.50 MiB** 源码目标；设备复测仍未完成。总包不会因搬分包而明显变小。
- 若要求首次离线交互也立即有完整音乐，则保留 BGM 主包，先无损图片优化，再试听 48 kbps AAC 候选。仅靠该路线不宜承诺主包降到 1.5 MiB。
- 若主要目标是减少所有主题的累计下载量，则另做十套图集无损压缩；这基本不改善经典主题的首次主包下载。

当前源码收益已经本地测量，但仍不是微信最终代码包尺寸。阶段 D 的音频重编码与阶段 E 的十套主题压缩没有实施，也不因 A–C 完成而自动授权。

## 3. 方案选择与预算推演

MiB = 1,048,576 bytes。以下均以当前源码字节为基线，不给出启动秒数承诺。

| 路线 | 主包估算 | 总包变化 | 体验代价/限制 |
| --- | --- | --- | --- |
| 只补三个精确忽略项 | 3,142,431 bytes / 2.997 MiB | 估算减少 38,924 bytes | 开发者工具可能本来就排除了它们，实际收益待确认 |
| 再做 Portal 同像素无损压缩 | 上一行减实际图片差额 | 同额减少 | 收益未实测，可能很小；不先许诺 50% |
| 音乐保留主包，改 48 kbps 完整 AAC | 约 2.60 MiB，未计图片收益 | 约少 0.40 MiB | 理论码率估算；需听感、循环和设备验收 |
| 音乐保留主包，改 32 kbps 完整 AAC | 约 2.21 MiB，未计图片收益 | 约少 0.79 MiB | 音质风险更高，仅对比候选，不作默认交付 |
| 保留原音乐质量，独立 `audio-bgm` 分包 | 搬移及忽略后的净基线 1,460,339 bytes / 1.393 MiB，再加少量代码 | 基本不变，新增入口/代码会略增 | 首次加载期间没有 BGM，短音效和游戏必须正常 |
| 十套正式图集无损压缩 | 主包基本不变 | 减少实测图像差额 | 不承诺大比例；保持像素与槽位协议 |

音频重编码模型：`时长 × 目标总码率 ÷ 8 + 容器开销`，以约 32 KiB 容器开销做粗估，实际编码结果可能不同。压缩 BGM 和搬 BGM 不能重复计算主包收益：若已经移出主包，再压缩它只减少音频分包和总包。

推荐音乐分包后的源码验收目标 ≤1.50 MiB，主包预算可在该阶段降至 **1.60 MiB** 留出小幅增长空间；现有单分包、总包门禁不放宽。理论净基线不是 1.393 MiB 的硬交付值，要计入新增代码、入口及配置。

要显著压低总包，则先拿一个主题做无损样本，测得压缩率再外推。没有候选文件和视觉验收前，不给“总包一定降到 8MB”之类数字。

### 7.4 音频服务的完整行为契约

1. 通过可选第四个参数注入 `{ subpackages }`，当前三参数构造及普通主包音频 fixture 保持兼容。App 使用已经注入的同一个服务，不创建第二实例。
2. `AudioService` 负责何时请求/何时播放，`SubpackageService` 负责下载和就绪，平台负责宿主 API。状态不写进存档，不增加“已经下载”的持久字段。
3. 首次用户交互、声音开启、非挂起且未销毁，才调用 `packageForAsset(bgm.src)` 和 `ensurePackage(name)`。分包完成前不创建 BGM context、不设置未就绪的 `src`，也不阻塞/await App 启动、点击或短音效。
4. 不能以“未注入 loader”推断一个已配置到分包的路径是主包文件。真实 App 必须注入成功；缺失能力时安全无 BGM，不提前访问分包路径。
5. 服务内同一在途请求只挂一个完成处理链，并利用现有共享 Promise 去重；连续点击不能不断添加回调、创建 context 或重新播放。
6. 完成时重新检查当前声音开关、用户解锁状态、挂起集合、销毁状态及请求代次。不捕获并信任请求发起时的旧布尔值。
7. 前后台与系统音频中断是两个独立原因。可扩展 `pauseAll(reason)` / `resumeAll(reason)`，无参保留原调用语义；App 分别传 `background`、`interruption`。只有所有原因解除才能恢复，`interruptionEnd` 不能在后台播放，`show` 不能越过仍在持续的中断。静音是设置状态，不由生命周期恢复函数解除。
8. 下载期间 hide 或发生中断，晚回调不得播放；包就绪可保留。回到前台且所有条件满足，恢复之前的播放意图，即使请求开始时尚无 `bgm` 对象也不能永久失声。不要只复用当前 `wasPlaying = !!bgm` 判断。
9. `dispose()` 必须幂等，先标记销毁/使请求代次失效，再暂停销毁所有 context；App 的 dispose 音频调用改为它。晚成功、晚失败、resume、unlock 均不得重建对象或播放。
10. 下载失败只影响 BGM；记录本次失败，不弹阻断游戏的对话框。后续普通触摸、tick、show 不自动无限重试；用户关闭再开启声音才允许新一次重试，不另增重试按钮或改文案。
11. 快速关声再开声且原请求仍在途时，仍只存在一个底层下载和一个有效完成处理链，按当前意图结算。失败重试后的旧回调不能覆盖新请求状态。
12. `ensurePackage` 同步抛错、拒绝、宿主不支持，以及音频创建/播放失败都必须被收敛；分包已就绪不等于解码播放成功。context 错误允许在明确重试时安全重建，不能反复自动下载已就绪的包。
13. BGM 保持 loop、音量 0.28、原曲和时长。五个短音效及 `soundEnabled` 存档键不变。不给源音频做重编码、裁短、加静音垫片或重复存储。

### 7.5 必须在错误实现下失败的回归测试

| 输入场景 | 必须断言 |
| --- | --- |
| 未解锁/启动即静音 | 分包调用 0，BGM context 0，启动不等待下载 |
| 开声后连续 unlock/点击 | 底层下载 1、完成处理和 BGM 对象不重复 |
| 下载未完成，同时 click/step/error/complete/victory | 短音效仍按原路径立即播放 |
| pending → 关闭声音 → 成功 | playCount 不增加，`soundEnabled` 为 false |
| pending → hide → 成功 → show | 后台不播放，show 后恢复合法意图 |
| hide + 中断 → 仅解除其中一个 | 仍不播放，两个都解除才恢复 |
| pending → dispose → 成功/失败 | 不创建、不播放、无未处理 rejection |
| failed → 普通点击多次 | 不新增请求；off→on 才发起一次重试 |
| failed → retry → 旧成功/旧失败 | 旧回调不提交新状态 |
| off→on 发生在 pending 中 | 无并行下载，无重复播放，不永久静默 |
| loader 缺失/不支持/同步抛错 | 不访问未就绪文件，游戏与 SFX 正常 |
| context 创建、play 或 onError 失败 | 无崩溃，显式重试可恢复，不泄漏 context |
| 重建整个服务模拟缓存被清理 | 不读取持久“已下载”，重新通过宿主确认 |
| 真实 App hide/show/中断/dispose | 不是只测孤立服务；确认正确原因参数及销毁路由 |
| 真实包分类与资源入口 | 原 BGM 路径不存在，目标存在，SFX 主包、主题映射顺序不变 |

`tests/project-config.test.js` 目前假定全部包都是主题，`tests/subpackage-service.test.js` 目前对每项访问 `themeIds[0]`，必须按主题项与音频项分开校验。不能删除循环、降低断言，或把精确数量改成“至少 10 个”以让测试变绿。
