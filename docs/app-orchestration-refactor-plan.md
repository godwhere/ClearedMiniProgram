## 1. 结论与完成目标

采用分阶段抽离职责，不一次性重写 App，不以减少到某个行数作为验收目标。

## 4. 每日存档适配模块

### 4.1 文件与公开入口

拟新增：`/Users/ethan/Projects/ClearedMiniProgram/src/services/daily-progress-adapter.js`。

模块采用无状态函数，不需要构造、启动、恢复或销毁实例。公开入口收束为：

| 入口 | 输入责任 | 输出责任 |
| --- | --- | --- |
| `readDay(store, dateKey)` | 当前 store 和日期 | 保持现有记录读取、缺失及异常回退结果 |
| `canEnter(store, input)` | 日期、dayId、entryLimit、entriesRemaining | 保持 `allowed`、`source` 和适用时的 `raw` 结构 |
| `recordEntry(store, payload, previousNumbers)` | App 已生成的入场 payload 和原次数基线 | 返回独立的 `accepted` 控制判定与 `result`；后者保持当前成功／失败字段、次数归一化与附加字段 |
| `recordCompletion(store, payload)` | App 已生成的完成 payload | 保持当前归一化结果，拒绝结果返回 `null` |

`recordEntry` 的 App 缺失方法提前返回仍在原位置；App 仅在确认方法存在并生成 payload 后进入该适配入口。不为此次拆分另增一套缺失 store 的入场业务规则。

模块必须每次使用传入的当前 store，保持 store 方法的接收者绑定；不在模块级缓存服务或错误状态。

### 4.2 App 与适配模块的分工

App 保留：

- 缺失入场 store 方法时的原提前返回；该路径仍不生成幂等键、不增加 nonce、不提交入场云操作。
- 日期、dayId、关卡 ID 列表、entryLimit 等业务输入的准备。
- 入场幂等键的格式、生成时机、原时间来源和 `dailyEntryNonce` 增量。
- 完成时间、elapsedMs、关卡数量及完成 payload 的生成。
- `authorityMode` 判断、云待办提交、`cloudQueued` 赋值和 observer 传递。

适配模块仅接管：

- 已有 store 方法选择及对象／位置参数转换。
- 现有异常、空结果和显式拒绝处理。
- 现有结果的归一化；保持原字段覆盖顺序，不删减附加字段。

`recordEntry` 的 `accepted` 只复现旧版“是否继续执行云入队等后续副作用”的控制分支，不能由归一化后的 `result.ok` 推导。原始结果可能同时包含 `ok: true` 与 `allowed: false`、`canEnter: false` 或 `error`；这些字段继续原样返回，但不得覆盖控制判定。本轮保留内置 store 第三次成功入场返回 `canEnter: false` 时不提交云待办的历史行为；是否修复这项历史漏入队须另行确认，不能混入等价抽离。

禁止适配模块读取时间、生成 ID、启动重试计时器、访问平台存储或调用云服务。它可以通过传入的 store 执行现有读写，因此“无状态”不等于“没有存档副作用”。

### 4.3 兼容回退必须逐项保留

| 原调用 | 原顺序及回退边界 |
| --- | --- |
| `canEnter` | 先位置参数。结果为 `null`／`undefined`，或单参数旧接口返回 `false` 时，才按原条件尝试对象参数；原异常处理保持不变 |
| `recordEntry` | 先对象参数。结果为空，或异常被转换为空后，才尝试位置参数 |
| `recordLevelCompletion` | 先对象参数。结果为空或调用抛错后，才尝试位置参数 |
| 旧 `recordCompletion` | 先对象参数；只有抛错才尝试位置参数，单纯返回空值不触发该回退 |

不得合并成通用“失败就换参数重试”。两参数 `canEnter` 明确返回 `false` 时，不得新增第二次调用。不得把没有可用写入结果解释成成功，也不得改变轻量宿主缺失完成 store 时的非持久化回退。

App 的业务入口方法签名和构造注入兼容保持不变。`dailyResultAllowed`、`dailyAllowedValue` 的内部规则可集中到适配模块；只有确认不再有调用者且不属于保留的宿主契约时，才可删除对应冗余辅助方法。不能留下两套以后会各自变化的结果判断规则；无法在现有边界内处理时应报告，不擅自扩大公开接口。

`dailyObject`、`dailyInteger` 等仍被其他 App 路径使用的辅助函数不得顺手移除、重命名或全局改写。

## 5. 每日 ViewModel 模块

### 5.1 文件与入口

拟新增：`/Users/ethan/Projects/ClearedMiniProgram/src/ui/view-models/daily-view-model.js`。

公开入口：`buildDailyViewModel(input)`。

只处理 `daily`／`dailyResult` 页面字段。App 继续取得基础模型、每日完成状态和棋盘 ViewModel，再合并该函数返回的字段。

### 5.2 输入与输出合同

输入由 App 显式组装，包含：

- 每日日期、dayId、challengeId、题面、关卡列表、关卡索引和各关结果。
- 入场次数、限制、剩余次数及调试无限次数标记。
- 每日完成状态、当前结果、入场与结果显示时间、累计耗时等现有展示数据。
- 已由 App 生成的 `boardView`、提示启用状态。
- 从现有配置读取的每日首次完成奖励金额。

不得把整个 App、整个 `this.daily`、Runner、store、平台或服务查询回调作为输入。`this.daily` 包含 Runner，不能借“上下文对象”名义整体传递。

输出保持 Renderer 已使用的字段名和语义，包括每日次数、关卡别名、提示、结果、棋盘与 Portal 回退字段；不借拆分清理看似重复的兼容字段。函数返回新的字段集合，由 App 按原顺序合并基础模型。

### 5.3 纯映射约束

- 不读取存档、系统时间、全局配置或外部可变状态。
- 不修改输入、触发 action、切换场景或绑定 Runner。
- 不缓存每日会话，不产生事件总线或订阅。
- 不额外调用 Runner 查询；`buildBoardViewModel()` 本轮保持原位与调用次数。
- 不新增每帧深拷贝、JSON 序列化或完整关卡集合重建。
- 保持原有必要引用语义，尤其不能替换 App 内被异步奖励回执持有的 `daily.result` 对象；传入展示对象必须只读使用。
- 缺失 board、提示不可用、Portal 缺失等情形保持当前回退；不硬编码当前奖励数值。

本轮不抽取首页、账号、普通游玩／结果、关卡分页、主题分页、走廊分页或特效分页分支，不移动其中的分页状态修正。

## 11. 未来扩展接口与升级触发条件

本轮保留实际可用的数据入口和职责边界，不添加无调用者的预留方法。

| 未来变化 | 优先扩展位置 | 何时重新评估架构 |
| --- | --- | --- |
| 每日 store 新旧调用形式或返回格式变化 | 适配模块及其契约测试 | 需要异步协议、改变持久化语义或增加业务授权时，重新制定边界 |
| 每日显示字段、按钮展示状态变化 | App 提供显式输入，ViewModel 映射，Renderer 消费 | 展示需求开始要求写入状态或调服务时，不得继续塞入 ViewModel |
| 新关卡来源、进度域或棋盘机制 | 现有 RunContext、completion policies 与 data-only manifest | 需要新进度写入合同或机制版本时，单独设计，不新增平行注册体系 |
| 新奖励或每日入场来源 | 现有奖励与授权入口 | 涉及新的授权、幂等或账号合同，另行确认服务与测试白名单 |

后续建议顺序：每日运行流程 → 其他场景 ViewModel → 账号与奖励流程分别评估。

每日运行流程的下一轮前提是：本轮兼容与模型契约已稳定，明确新流程对象是否拥有会话状态，以及 App 和流程之间的账号校验、异步取消、生命周期与回执归属。不能将整套 App 引用作为所谓扩展接口，也不能让 App 与新流程同时成为状态所有者。

后续阶段不在本轮运行代码白名单内，不能因本节出现路线图就自动创建对应模块。
