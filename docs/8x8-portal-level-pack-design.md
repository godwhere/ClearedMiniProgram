## 0. 设计目标与落地原则

本章不再重复 8×8 棋盘教学，而是用 30 关建立 Portal 的完整学习曲线。所有
关卡固定为 `8×8 + portal@2`：一个中性传送网络、每条线路最多一次传送、
入口段/出口段必须分手势完成。当前候选不加入炸弹、可重复路径或其他未发布机制。

题面采用“解法优先”流程：先生成覆盖棋盘的互不重叠路径，再选取一个非相邻
入口/出口替换为传送边，最后从路径首尾反推出端点。这样可以先保证规则可解，
再通过端点密度、线路长度、传送距离和诱饵门数量调节难度。

正式接入时建议把这些关卡追加到现有 `clearedset8` 数据组尾部（内部仍是
`setIndex=4`），而不是新建并复用已退休的 `setIndex=5`。后者会与旧版 8×10
存档键冲突。每关必须新增稳定 `Id`，Portal 解答放入按 ID 索引的独立表，
不能塞进无 Portal 的普通 `data/solutions.js` 平铺数组。

## 0.1 当前 Portal v2 发布契约

- 题面必须声明 `Mechanic: 'portal'`、`PortalRulesVersion: 2`、`Portals`。
- 每关恰好一个网络；网络至少两个 `Cells`，可包含不参与覆盖的诱饵门。
- 门格不能是端点、`Blocked` 或重复格；本批暂不使用 `Blocked`。
- 每条线路最多一次传送；标准解必须显式写 `Exit.PortalId/From/To`。
- 段内只允许四方向相邻移动；传送只发生在分段之间，不绘制跨棋盘直线。
- v2 门格不属于 required coverage；未使用诱饵门保持空置是合法结果。
- 正式发布必须同时通过 `validatePortalLevel(..., { requireSolution: true })` 和
  逐段 `GameRunner` 回放，并得到 `WON`。

## 生成与复现说明

这份候选稿由固定种子的 8×8 Hamilton 路径生成器产生：先在行优先棋盘上用
Warnsdorff 排序的 DFS 找到完整路径，再按分档选择 Portal 入口/出口位置，
把中间区间切成若干条线路。第 6 关起的诱饵门从路径中排除，因此不会在标准
解中意外触发；它们只用于测试 v2 的“未使用门可留空”语义。

生成器不是发布脚本，也不属于运行时代码。后续若需要重新生成候选，必须固定
随机种子并把生成结果与本文件的 `Lines`、`Portals`、`Segments` 逐项比较；
不能因为随机路径变化而静默替换已评审题面。正式落地时应将生成器迁入受审计的
内容工具，或直接把评审后的 JSON 锁定为源文件。

## 共通约束

- 棋盘 8×8，行优先索引 `r*8+c`；每关一个网络 `P1`。
- `Portals.Cells` 第 1、2 个是标准解入口/出口，其余为诱饵门（v2 可不覆盖）。
- `Lines` 只声明端点；`Solution` 按同顺序给出 `Segments`，每个 `Exit` 明确 `PortalId/From/To`。
- 设计验证：`validatePortalLevel(level, solution).ok === true`，并用 GameRunner 逐手势回放得到 `WON`。

本文后面的“精确题面与解法”就是本批的可审阅内容源；其中数组可直接转换为
未来的 `clearedset8.json` 与按 ID 索引的 Portal solution manifest，但在转换前
仍须补充正式色板、唯一解检查、难度试玩和发布 ID 审批。

分档不是运行时难度字段；它只用于策划、试玩和后续调参。候选生成器目前
保证“存在一条可回放解”，没有证明玩家视角下的唯一解。正式锁定前要额外检查：

- 是否存在明显比标准解更短、更直的旁路；
- 诱饵门是否能被玩家理解为可选而不是故障；
- 线路顺序是否产生合理的规划感，而不是单纯依赖试错；
- 入口提示、出口高亮和长路径在小屏上是否仍可辨认。

## 后续机制预留（本批不实施）

本批 30 关固定为 `8×8 + portal@2`。下面只记录未来机制的设计边界，
不向本批题面、解法、`GameRunner` 或 UI 里埋入未实现字段。

### A. 可重复路径：`retrace@1`

“重复走”需要先区分两种含义：

1. **同一线路自重访**：允许当前线路再次经过自己已经走过的格，建议每格
   设置明确的 `MaxVisitsPerCell` 上限（首版可默认 2），并在解答中显式记录
   重访步骤；
2. **不同线路共享已占格**：这会改变 `owner`、完成判定和撤销语义，应另立
   `shared-path@1`，不能偷偷放宽现有占用规则。

首版 `retrace@1` 仍禁止跨线共享、重复端点和重复 Portal；快照、Undo、
`touchcancel` 与提示搜索必须同时保存/消费访问次数。它不能通过修改
`PortalRulesVersion` 来启用。

### B. 炸弹九宫格：`bomb@1`

建议使用独立题面形状，而不是把 `portal+bomb` 拼成机制字符串：

```js
{
  Mechanic: 'bomb',
  BombRulesVersion: 1,
  Bombs: [{ Id: 'B1', Cell: 27 }]
}
```

首版需要先冻结以下语义：

- 首次合法进入炸弹格时触发，还是松手时触发；
- 炸弹是否一次性消耗；
- 以炸弹为中心向四周裁剪的 3×3 footprint，越界格如何处理；
- 被摧毁格是否变为不可进入、是否从 required coverage 中移除；
- 是否允许摧毁端点、已提交线路、另一枚炸弹。

推荐 `bomb@1` 只允许静态安全 footprint：端点、已有线路和其他炸弹不得
落入爆炸范围；受影响格进入 `destroyedMask` 后不可再走且不计 required
coverage。会切断既有线路、连锁引爆或改变端点的版本另立 `bomb@2`。

炸弹结果必须由纯函数从中心格计算，解答只记录触发步骤和 Bomb ID，不能
信任作者在答案中手写的九宫格数组。爆炸状态、动画锁、Undo、重置、后台
取消和回放都必须原子一致。

### C. 组合机制与施工顺序

第一次需要 Portal、重复路径和炸弹组合时，再引入显式：

```js
{
  Mechanics: [
    { Id: 'portal', RulesVersion: 2 },
    { Id: 'retrace', RulesVersion: 1 }
  ],
  CompositionVersion: 1
}
```

组合必须有兼容矩阵和确定的事件顺序；未知机制、版本或组合在发布校验中
直接拒绝，运行时对坏数据安全降级但不能执行内容携带的脚本。

推荐施工顺序：

1. 先完成本批 Portal 30 关的 UI、提示、发布校验和真机验收；
2. 单独实现并验证 `retrace@1` fixture；
3. 单独实现并验证 `bomb@1` fixture；
4. 最后再评审组合机制和新的解答事件流。

## 后续正式接入边界

当本设计稿通过评审后，正式接入应分成独立提交：

1. 将本文 `Levels` 追加到现有 `clearedset8.json` 尾部，保留内部
   `setIndex=4`，避免复用已退休 8×10 的存档坐标；修改 JSON 后运行

3. 在 `RunContext` 中保持 `source: catalog`、`progressionScope: ordinary`，
   让现有连续解锁自然延伸到第 92 关；Portal 只是机制，不改变进度域。
4. 增加发布测试：ID 唯一、端点/门格无冲突、每线一次传送、诱饵门可留空、
   所有必需格覆盖、逐段回放为 `WON`，以及普通/Portal/daily 进度隔离。
5. UI 只消费结构化 ViewModel。当前另一对话的 Portal UI 调整完成并验收前，
   本批不修改 `CanvasRenderer`、`PortalOverlay` 或提示文案契约。

## 当前结论

这 30 关已经形成可审阅、可复现、带完整标准解的 Portal 8×8 内容包；
它们现在仍是候选题面，不代表已完成唯一解、难度或设备验收。未来新增的
8×8 普通关应继续追加在本包之后，连续编号和分页由 catalog 自动计算，
不得复用已发布 ID 或旧存档坐标。
