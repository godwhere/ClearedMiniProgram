## 0. 设计目标与落地原则

本章不再重复 Portal 基础教学，而是检验多色线路与跨区拓扑的共同规划。当前产品
阶段固定使用 `8×8 + portal@2`、一个两门网络、每条线路最多一次传送；四门网络
推迟到 100 关以后单独教学。当前内容不加入炸弹、可重复路径或其他未发布机制。

第 1–5 关采用“普通玩法优先”的解法骨架：先保留长度均衡、彼此争夺空间的多条
普通路径，再用两个内部格重组其中两片区域，形成一条分段 Portal 线路。Portal
可以是必需路线，也可以存在经过审查的高成本无门解；廉价直连旁路不允许发布。

本次接入将这些关卡追加到现有 `clearedset8` 数据组尾部（内部仍是
`setIndex=4`），而不是新建并复用已退休的 `setIndex=5`。后者会与旧版 8×10
存档键冲突。每关必须新增稳定 `Id`，Portal 解答放入按 ID 索引的独立表，
不能塞进无 Portal 的普通 `data/solutions.js` 平铺数组。

## 0.1 当前 Portal v2 发布契约

- 题面必须声明 `Mechanic: 'portal'`、`PortalRulesVersion: 2`、`Portals`。
- 每关恰好一个网络；当前内容阶段的网络必须正好包含两个 `Cells`。
- 门格不能是端点、`Blocked` 或重复格；本批暂不使用 `Blocked`。
- 每条线路最多一次传送；标准解必须显式写 `Exit.PortalId/From/To`。
- 段内只允许四方向相邻移动；传送只发生在分段之间，不绘制跨棋盘直线。
- v2 门格不属于 required coverage；不用 Portal 的完整解可以合法留空两个门格，
  但必须通过旁路难度审查。
- 正式发布必须同时通过 `validatePortalLevel(..., { requireSolution: true })` 和
  逐段 `GameRunner` 回放，并得到 `WON`。

## 生成与复现说明

第 1–5 关从已验证的均衡多线路骨架出发，通过路径合并、跨区重组、旋转或镜像得到
新的端点关系，再锁定本文记录的题面和解答。它们不是运行时生成内容。

第 6–30 关仍来自旧的固定种子 Hamilton 路径生成器。旧流程虽然可以快速证明可解，
却产生了超长主线、凑数短线和过多门格，不能继续作为正式出题方法。后续重做时应
逐批替换题面和解答，保留稳定 ID，不得用随机结果静默覆盖已评审内容。

## 共通约束

- 棋盘 8×8，行优先索引 `r*8+c`；每关一个网络 `P1`。
- 第 1–5 关的 `Portals.Cells` 正好两个；两格是标准解入口/出口。
- `Lines` 只声明端点；`Solution` 按同顺序给出 `Segments`，每个 `Exit` 明确 `PortalId/From/To`。
- 设计验证：`validatePortalLevel(level, solution).ok === true`，并用 GameRunner 逐手势回放得到 `WON`。
- 8×8 专章不设置基础操作 `Instructions`；LOCKED/WAIT 动态提示仍由运行时提供。
- 第 1–5 关还必须满足 5–6 色、每线 8–16 格、最长线不超过 25% 和无凑数短线。

本文后面的“精确题面与解法”就是本批的可审阅内容源；这些数组已经转换到
当前的 `clearedset8.json` 与按 ID 索引的 Portal solution manifest。
第 1–5 关已经完成有门解、无门旁路分类和自动质量检查；仍须补充难度试玩。
第 6–30 关继续视为待重做候选。

## 后续机制预留（本批不实施）

本章 30 关固定为 `8×8 + portal@2`。下面只记录未来机制的设计边界，
不向本批题面、解法、`GameRunner` 或 UI 里埋入未实现字段。

### A. 可重复路径：`retrace@1`

“重复走”需要先区分两种含义：

1. **同一线路自重访**：允许当前线路再次经过自己已经走过的格，建议每格
   设置明确的 `MaxVisitsPerCell` 上限（首版可默认 2），并在解答中显式记录
   重访步骤；
2. **不同线路共享已占格**：这会改变 `owner`、完成判定和撤销语义，应另立
   `shared-path@1`，不能偷偷放宽现有占用规则。

首版 `retrace@1` 仍禁止跨线共享、重复端点和重复 Portal；快照、Undo、
`touchcancel` 与提示搜索必须同时保存/消费访问次数。它不能通过修改
`PortalRulesVersion` 来启用。

### B. 炸弹九宫格：`bomb@1`

建议使用独立题面形状，而不是把 `portal+bomb` 拼成机制字符串：

```js
{
  Mechanic: 'bomb',
  BombRulesVersion: 1,
  Bombs: [{ Id: 'B1', Cell: 27 }]
}
```

首版需要先冻结以下语义：

- 首次合法进入炸弹格时触发，还是松手时触发；
- 炸弹是否一次性消耗；
- 以炸弹为中心向四周裁剪的 3×3 footprint，越界格如何处理；
- 被摧毁格是否变为不可进入、是否从 required coverage 中移除；
- 是否允许摧毁端点、已提交线路、另一枚炸弹。

推荐 `bomb@1` 只允许静态安全 footprint：端点、已有线路和其他炸弹不得
落入爆炸范围；受影响格进入 `destroyedMask` 后不可再走且不计 required
coverage。会切断既有线路、连锁引爆或改变端点的版本另立 `bomb@2`。

炸弹结果必须由纯函数从中心格计算，解答只记录触发步骤和 Bomb ID，不能
信任作者在答案中手写的九宫格数组。爆炸状态、动画锁、Undo、重置、后台
取消和回放都必须原子一致。

### C. 组合机制与施工顺序

第一次需要 Portal、重复路径和炸弹组合时，再引入显式：

```js
{
  Mechanics: [
    { Id: 'portal', RulesVersion: 2 },
    { Id: 'retrace', RulesVersion: 1 }
  ],
  CompositionVersion: 1
}
```
